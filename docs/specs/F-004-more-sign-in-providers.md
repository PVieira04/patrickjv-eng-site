## Summary

F-002 made signing in with Google the way a booking is confirmed. People without a Google account, or whose company runs on Microsoft 365, are left with `/book`'s email form, and their agents can't book for them at all. F-004 adds **Sign in with Microsoft** (work, school and personal accounts) and **Sign in with Altimist ID** as more buttons on the same confirm page. Each provider's only job is to produce F-002's `person` and `grant`; the booking core, caps, failure rules and cancellation stay as they are.

MCP URL-mode elicitation, which F-002 listed under P2, is **out of scope**: the protocol changed it in 2026-07-28 and the major clients don't reliably support it yet (research, 9 Oct 2026). The confirm link stays in the tool result.

## Build delta (revision of 11 Nov 2026)

PR #12 built the first version of this spec. The behaviour below is what this revision changes or adds, each detailed in the decision or criterion named; everything else in the spec is already built.

1. **Trial marks (D7):** HMAC-SHA256 marks keyed with `SIGNIN_TRIAL_KEY`, made and checked through one shared module, `npm run trial-link`, and the trial button's form carrying the mark. Today `try=` alone shows a trial provider.
2. **Credentials in health (D6):** `credentials` per enabled provider, from a probe of each token endpoint and from real code exchanges, stored in the booking store's `health` table with the time of the last decisive result, which goes stale after 24 hours. The probe's request (D6's shape, Microsoft at the home tenant) and the reading of its answer live in one shared module, `lib/credentials-probe.mjs`, used by the Worker and by a new `npm run probe-check -- <provider>`, the manual check's tool. Decisive probes are held for an hour, indecisive ones retried after a minute. "Expiring" only while Microsoft is launched.
3. **Health's fetches (D7):** the calendar token refresh (`mcp/booking-service.js` line 259, today awaited before anything else, with `mcp/booking-google.js`'s 20-second `TIMEOUT_MS`), the discovery fetches and the probes run in parallel, each with a 4-second timeout for health; `ping` takes that timeout, and a refresh that times out reuses the cached result; the shape health returns when the store can't be used.
4. **Sign-up return page (Flow 2):** `GET /book/confirm?signed_up=1`, with its fallback line.
5. **The "Create one" link (Flow 2):** the fixed URL whose `return_to` carries no ticket (today's link carries the confirm page's URL), opening in a new tab with `target="_blank" rel="noopener noreferrer"` (today's, `mcp/handler.js` line 954, has neither), shown wherever the Altimist ID button is: the confirm page, `/book` and the homepage's in-page sign-in prompt.
6. **D8 boundaries:** `ALLOWED_MENTIONS` in `build.mjs` gains left-hand boundaries and the `@` rule for the host, allows a `.` after a form only when no word character follows it, and drops the percent-encoded `try%3Daltimist`. The Worker's D8 test covers the sign-up return page as well as the confirm and cancel pages.
7. **`book_meeting`'s `next_step` (D7):** names the ready list, not the launched list.
8. **Config validation (D6, D7):** `signin.providers` must include `"google"` anywhere in the list, in the build and in `mcp/booking-config.js` (line 70 requires it first today). Both also validate the new `signin.credentialsProbeVerified` and, while Microsoft is enabled, `signin.microsoftTenantId`.
9. **Shared token rules:** `aud`, `iss`, `exp`, `iat`, `nbf` and `nonce` in the one shared check, with `nbf` given the same 5-minute leeway as `iat` and applied to every provider (today only Microsoft checks `nbf`, with no leeway).
10. **Cancel starts (D7):** accepted only for the booking's own provider, never needing a mark.
11. **`healthVerdict` (`lib/smoke-lib.mjs`):** a provider entry gains `credentials`; the verdict takes the verified list as well as the launched list and gains warnings, which `smoke.mjs` prints as WARN. A launched provider whose `credentials` isn't `"ok"` fails the check when it is verified and is a WARN when it isn't; launched Microsoft with an expiring secret fails either way (D6).
12. **Runbook (`docs/06-operations.md`):** "Rotate the Microsoft sign-in secret" closes with `credentials: "ok"` in the smoke output, and says that a test sign-in clears a rejection at once while the probe clears it within the hour; new entries cover `credentials` `"rejected"`, `"unknown"` and `"expiring"` for any provider, as a failure or as a WARN.
13. **One expiry computation (D6):** `lib/secret-expiry.mjs` works out days to 00:00 UTC on `signin.microsoftSecretExpires`; `build.mjs`'s `checkMicrosoftSecret`, health and the smoke check all call it (today the build does the sum inline).
14. **The in-page sign-in prompt's sentence (`public/index.html` line 1025):** "Nothing is booked until you sign in with …" names the ready list from `signin_providers`, the list its buttons come from; today it uses the launched list the build embedded (`d.sign_in_providers`).

## User Stories

### US-1: Confirm with my Microsoft account

As **a person whose work email runs on Microsoft 365, or who has an Outlook.com account**, I want **to confirm the booking my agent made by signing in with Microsoft**, so that **I don't need a Google account**.

### US-2: Confirm with Altimist ID

As **a person with an Altimist ID**, I want **to confirm with it, or create one on the way**, so that **I can use the passkey I already have**.

### US-3: Cancel with the account I booked with

As **a guest**, I want **cancelling to accept the same account I confirmed with**, so that **the provider I chose doesn't matter later**.

### US-4: Only offered what works

As **a person on the confirm page**, I want **to see only the sign-in options that are switched on and set up**, so that **I don't hit a button that can't work**.

---

## Goals & Non-Goals

**Goals**
- Microsoft and Altimist ID confirm and cancel exactly as Google does in F-002, through `confirmRequest` and `cancelMeeting`.
- The address used for the invite is one the provider stands behind (rules per provider, D3–D4).
- A provider is offered only when it's launched and its secrets are set; launching one is a config change, not a code change.
- Cost stays at £0.

**Non-Goals**
- MCP URL-mode elicitation (see Summary).
- Linking accounts: a person who signs in with Google one day and Microsoft the next counts as two people for the per-person caps. Accepted: the caps exist to bound abuse, and the daily and global caps still apply.
- Agents signing in with their own identity (F-002 P4).
- Retiring the email form (F-002 P3).
- Microsoft Graph or any scope beyond sign-in.

| D6 | **The Microsoft secret's expiry is guarded like `security.txt`, and every provider's client credentials are checked at runtime, by a probe and by real sign-ins. Each provider's probe reports only, and fails nothing, until a manual check has shown that it reads that provider correctly** (probe decided with Patrick, 11 Nov 2026; report-only until verified, decided with Patrick, 11 Nov 2026). **Expiry:** the date lives in `booking.json` (`signin.microsoftSecretExpires`, `YYYY-MM-DD`). One function (`lib/secret-expiry.mjs`) turns it into days left, from now to 00:00 UTC on that date, so the number goes negative once the date has passed; the secret counts as **expiring** when it is 30 or less. The build (`checkMicrosoftSecret`), health and the smoke check all call that function, so they can't disagree about the day. Whenever `microsoft` is launched (D7), the build fails if the date is missing or malformed, or while the secret counts as expiring, as for `security.txt`'s `Expires`. While Microsoft isn't launched, on trial included, the build, health and smoke all ignore the value, so a trial needs no date and never reads as expiring. **After the date passes**, health keeps saying `"expiring"`; there is no separate "expired" value. Microsoft answers an expired secret with `invalid_client` (AADSTS7000222), so the next probe or sign-in turns it `"rejected"` anyway, the build already refuses to deploy, and the smoke check fails on either; a fifth value would need handling everywhere for the same action, rotating the secret. A build only runs on a push, and a secret can be deleted, revoked or mistyped before its date, so the Worker also checks the credentials themselves. **Probe request:** for each enabled provider whose secrets are set, health posts to the provider's token endpoint what a real code exchange sends: `grant_type=authorization_code`, our client ID and secret (sent the way the real exchange sends them), our registered `redirect_uri` (`https://patrickjv.com/book/callback/<provider>`), a dummy code and a dummy PKCE verifier. The code is fresh each time and shaped like an ordinary one (32 random bytes, base64url, 43 characters) rather than empty or obviously broken, so a provider that parses the code before anything else still gets past it. The verifier is a fresh 43-character base64url value, the shortest RFC 7636 (4.1) allows. The request is therefore valid in every respect except that no provider issued the code. **Microsoft is probed at the app's home-tenant token endpoint** (`https://login.microsoftonline.com/<tenant ID>/oauth2/v2.0/token`, with the tenant ID in `booking.json` as `signin.microsoftTenantId`, a GUID, required while Microsoft is enabled and validated in the build and at Worker start), not at `/common`. In its home tenant the app and its secret are known before the code is looked at, so Entra can authenticate the client first. That ordering is this design's assumption and **is not verified**: Microsoft doesn't document the order in which it checks a token request, and the manual check is the proof. The probe runs in parallel with health's other fetches, with the same 4-second timeout (D7), carries no visitor data and creates no transaction. **Reading the probe's answer** (the OAuth `error` in the body, RFC 6749 5.2, which allows a 400 or a 401 for it). The probe has no visitor, so every reading applies to the provider as a whole: `invalid_grant` is **ok** (the client was authenticated and only the code was refused, which is what a working secret should get), and only `invalid_grant`; `invalid_client` is **rejected** (the secret or client ID is wrong, expired or deleted: Microsoft's AADSTS7000215 and AADSTS7000222); `unauthorized_client` is also **rejected**. From a real sign-in it can come from one visitor's tenant, but the probe goes to the app's own tenant with no visitor, where it means the app itself can't make this request (for example AADSTS700016, app not found in the directory, or AADSTS7000112, app disabled), so nobody can sign in. It counts as rejected rather than getting a value of its own because the alert and its first step are the same (look at the app registration), and the recorded error says which it was. `invalid_request`, `unsupported_grant_type`, `redirect_uri_mismatch`, `invalid_scope` or any other OAuth error is **unknown**, with the error recorded: the provider answered, but in a way that says nothing about the secret, because the probe's request is wrong or the registration has changed. Because that answer is definite, it clears the stored result, so `credentials` reads `"unknown"` at once rather than vouching with an older ok. A 429, `temporarily_unavailable`, a 5xx, a timeout, a network error or a body that isn't an OAuth error is **unknown** and transient: it leaves the stored result as it was, subject to the 24-hour rule below. The recorded error is the OAuth `error` code and, for Microsoft, the AADSTS number, never `error_description`'s text; it is stored with the result and logged with the subsystem (`signin_probe`) and the provider. **Cadence:** after a decisive probe (ok or rejected) the booking Durable Object waits an hour before probing that provider again, however often health is called. After an unknown one it probes again on the next health call a minute or more later, as for discovery fetches (D7), so the post-deploy smoke's retries (five attempts over about three minutes, `.github/workflows/monitor.yml`) can see a decisive answer after a first probe that timed out. Probes only run inside health calls, so in practice they happen when the smoke check runs, every 6 hours and after each deploy. Two calls arriving together may both probe. Health reuses the stored result in between. **Real exchanges** also count: `invalid_client` means rejected and a successful exchange means ok; anything else (`invalid_grant` from a reused or stale code, `unauthorized_client`, a 5xx, a timeout) changes nothing, since a visitor or an outage can cause it. `unauthorized_client` from a real exchange in particular can be specific to the visitor's tenant (an app disabled there), so it must not mark the provider rejected for everyone (Microsoft Learn, error code reference, checked 11 Nov 2026). **State:** per provider, the booking store's `health` table keeps the latest decisive result (ok or rejected, from a probe or a real exchange, whichever came last) and when it was recorded, the last recorded error, and the time and outcome of the last probe, so they survive a Durable Object restart. Health's `credentials` is `"rejected"` when the decisive result is a rejection less than 24 hours old; otherwise `"expiring"` when the provider is Microsoft, Microsoft is launched and the secret counts as expiring; otherwise `"ok"` when the decisive result is ok and less than 24 hours old; and otherwise `"unknown"`: there is no decisive result yet, or it is 24 hours old or more (so a probe that has failed transiently for a day stops vouching for an old answer), or a probe has answered with an unexpected OAuth error since it. **Report-only until verified:** `booking.json` gains `signin.credentialsProbeVerified` (an array, default `[]`; only `google`, `microsoft` or `altimist`, no duplicates, else the build fails, tested for each case; a provider listed but not enabled is ignored). A provider is added only after its manual credentials check (Acceptance Criteria, manual checks) is recorded in the spikes log. Health reports `credentials` the same way whether a provider is listed or not; the smoke check is what differs. For a launched provider that is listed, `credentials` other than `"ok"` fails the check. For one that isn't, `"rejected"` and `"unknown"` are a WARN naming the provider and value, which the monitor shows but which doesn't fail the run. Expiry is not report-only: the smoke check fails whenever Microsoft is launched and the shared function says its secret is expiring, verified or not, so an unverified Microsoft whose lapsed secret already reads `"rejected"` still fails. This applies to Google too: it has been launched since F-002, but its probe reports only until Google's manual check is recorded and `"google"` is added to the list. Once a provider is verified, a secret revoked between monitor runs fails the next run (every 6 hours) with no sign-in needed. A rejected provider keeps its button: the signal is for Patrick, and hiding the button fixes nothing. Rotation is a runbook entry; after it, a test sign-in returns `credentials` to `"ok"` at once, and the next probe does within the hour. **On the provider's side:** each probe is a failed token request, so it will show among the app's failed sign-ins in Entra's logs (which log was not checked). Microsoft documents lockout (smart lockout) for user passwords; we found nothing documented about locking or throttling an app's client credentials after failed requests (unverified), and a probe an hour per provider, or one a minute while the answers are indecisive and health is being called, is far below any published request limit. That each provider authenticates the client before it looks at the code, and answers a wrong secret with `invalid_client`, is assumed from RFC 6749 (and, for Microsoft, from probing the home tenant) and is unverified for all three; that is why each probe reports only until its manual check passes. | Remembering: a sign-in that silently stops working when the secret lapses. The build check alone: misses a secret revoked early, and an expiry with no push in the 30 days before it. Real exchanges alone: a quiet site could run on a dead secret for weeks. Failing the smoke check on a probe nobody has checked against the provider: a misread answer would fail the monitor, or pass it, for reasons nobody has seen. Counting `unauthorized_client` from real exchanges: one visitor's tenant policy would flag the provider for everyone. Probing Microsoft at `/common`: the code may be parsed before the client is known, so a wrong secret could read as ok. An "expired" value: the same action as "rejected" and "expiring", with one more case everywhere. |

## User Flows

### Flow 1: Confirm with Microsoft or Altimist ID

1. As F-002 Flow 1 up to the confirm page.
2. The person clicks "Sign in with Microsoft" (or Altimist ID). `POST /book/confirm/microsoft` creates a `signin_tx` bound to the ticket, purpose and provider, sets the `__Host-` cookie and redirects to the provider with PKCE (S256), `state` and `nonce`.
3. The provider returns to `/book/callback/microsoft`. The site consumes `state`, exchanges the code server-side, checks the ID token as D3 (or D4) says, builds `person` and `grant` (`proof: "signin:microsoft"` or `"signin:altimist"`), and calls `confirmRequest`.
4. From here it's F-002: booked, declined or being finished.

### Flow 2: Create an Altimist ID on the way

Under the Altimist ID button, wherever it shows (the confirm page, `/book` after a time is picked, and the homepage's in-page sign-in prompt), "No Altimist ID? Create one" opens, in a new tab (`target="_blank" rel="noopener noreferrer"`), `https://altimist.id/signup/self-service?app_id=patrickjv-com&return_to=https%3A%2F%2Fpatrickjv.com%2Fbook%2Fconfirm%3Fsigned_up%3D1` (Altimist ID's self-service contract, checked 12 Oct 2026: it requires `app_id` and a `return_to` whose origin is allow-listed for that app). The `return_to` is the same for everyone and carries no ticket. A ticket is a bearer credential (under F-002, whoever signs in on its confirm page becomes the booked person), and anything in `return_to` reaches Altimist ID's logs and analytics. The confirm page's `Referrer-Policy: same-origin` already keeps its own URL out of the `Referer`. After sign-up, Altimist ID returns the new tab to `/book/confirm?signed_up=1`, which shows no form and says, in words that fit all three starting points: "Your Altimist ID is ready. Go back to the tab where you were booking and choose Sign in with Altimist ID. If that tab has gone, open the link from your assistant again, or start again at patrickjv.com/book." The last sentence is for in-app browsers, where the first tab may have closed or may not be reachable, and for the homepage's in-page prompt, which is gone once its tab is reloaded or closed. The confirm page is still open in the first tab with its ticket (and any trial pair) unchanged, the in-page prompt is still on the homepage with its request, and `/book` still has the chosen time (its request is created only on the first sign-in click), so nothing has to be carried across. If the ticket has expired by then, that tab's sign-in shows F-002's "expired" page. `signed_up=1` only has meaning without a ticket: with `t=` present, the parameter is ignored and the confirm page renders for that ticket as it would without it (no link of ours ever produces that URL).

### Flow 3: Cancel

As F-002 Flow 3: a sign-in whose `provider` and `subject` match the guest cancels. A cancel link offers **only the booking's own provider** ("You booked with Microsoft. Sign in with Microsoft to cancel."), because no other account can cancel it. If that provider isn't ready, the page says so and points to the "Booked" email's cancel link, as the start-refusal rule below describes. A sign-in with the right provider but a different account changes nothing ("This booking belongs to someone else").

## Edge Cases

- **Microsoft "needs admin approval":** should be rare after publisher verification; if it happens, the person signs in another way. Nothing on our side can fix an organisation's consent policy.
- **Microsoft guest accounts:** `/common` signs people in to their home tenant, so `tid` is their home tenant; the key is stable.
- **A personal Microsoft account without an `email` claim:** refused as above (can happen for phone-number-only accounts).
- **Altimist ID sign-up takes longer than the ticket lasts:** the confirm page shows "expired", with F-002's advice to ask again.
- **A Microsoft secret expires or is revoked early:** every code exchange and probe gets `invalid_client`; health's `credentials` turns `"rejected"` at the first sign-in or the next probe, whichever comes first, and the next monitor smoke fails if Microsoft is verified, or warns if it isn't; once the date in `booking.json` is 30 days or less away, the smoke fails either way (D6). The button stays.
- **One visitor's tenant blocks the app** (`unauthorized_client`, for example the app disabled in that tenant): that sign-in fails as any failed exchange does; `credentials` is unchanged, because the problem is that tenant's, not our secret's (D6). The probe getting `unauthorized_client` is different: it asks the app's own tenant with no visitor, so it means the app is unusable for everyone, and reads as rejected.
- **A provider's token endpoint is slow or down for a day:** each health call retries the probe after a minute; once the last decisive result is 24 hours old, `credentials` reads `"unknown"` (D6), and the smoke fails for a verified provider.
- **Google's calendar API hangs:** health still answers in about 4 seconds, reporting the last calendar result it has (D7).
- **A provider goes down mid-flow:** the callback's code exchange fails; F-002's rule applies (the transaction is spent, the ticket isn't).
