## Summary

F-002 made signing in with Google the way a booking is confirmed. People without a Google account, or whose company runs on Microsoft 365, are left with `/book`'s email form, and their agents can't book for them at all. F-004 adds **Sign in with Microsoft** (work, school and personal accounts) and **Sign in with Altimist ID** as more buttons on the same confirm page. Each provider's only job is to produce F-002's `person` and `grant`; the booking core, caps, failure rules and cancellation stay as they are.

MCP URL-mode elicitation, which F-002 listed under P2, is **out of scope**: the protocol changed it in 2026-07-28 and the major clients don't reliably support it yet (research, 9 Oct 2026). The confirm link stays in the tool result.

## Build delta (revision of 11 Nov 2026)

PR #12 built the first version of this spec. The behaviour below is what this revision changes or adds, each detailed in the decision or criterion named; everything else in the spec is already built.

1. **Trial marks (D7):** HMAC-SHA256 marks keyed with `SIGNIN_TRIAL_KEY`, made and checked through one shared module, `npm run trial-link`, and the trial button's form carrying the mark. Today `try=` alone shows a trial provider.
2. **Credentials in health (D6):** `credentials` per enabled provider, from an hourly probe of each token endpoint and from real code exchanges, stored in the booking store's `health` table; only `invalid_client` counts as a rejection; "expiring" only while Microsoft is launched.
3. **Health's discovery fetches (D7):** run in parallel with the probes, each with a 4-second timeout; the shape health returns when the store can't be used.
4. **Sign-up return page (Flow 2):** `GET /book/confirm?signed_up=1`, with its fallback line.
5. **The "Create one" link (Flow 2):** the fixed URL whose `return_to` carries no ticket (today's link carries the confirm page's URL), shown wherever the Altimist ID button is: the confirm page, `/book` and the WebMCP popup.
6. **D8 boundaries:** `ALLOWED_MENTIONS` in `build.mjs` gains left-hand boundaries and the `@` rule for the host, allows a `.` after a form only when no word character follows it, and drops the percent-encoded `try%3Daltimist`.
7. **`book_meeting`'s `next_step` (D7):** names the ready list, not the launched list.
8. **Order-free validation (D7):** `signin.providers` must include `"google"` anywhere in the list, in the build and in `mcp/booking-config.js` (line 70 requires it first today).
9. **Shared token rules:** `aud`, `iss`, `exp`, `iat`, `nbf` and `nonce` in the one shared check, with `nbf` given the same 5-minute leeway as `iat` and applied to every provider (today only Microsoft checks `nbf`, with no leeway).
10. **Cancel starts (D7):** accepted only for the booking's own provider, never needing a mark.
11. **`healthVerdict` (`lib/smoke-lib.mjs`):** a provider entry gains `credentials`, and a launched provider whose `credentials` isn't `"ok"` fails the check.
12. **Runbook (`docs/06-operations.md`, "Rotate the Microsoft sign-in secret"):** the closing check becomes `credentials: "ok"` in the smoke output, and says that a test sign-in clears a rejection at once while the probe clears it within the hour; a new entry covers a `credentials: "rejected"` alert for any provider.

## User Stories

### US-1: Confirm with my Microsoft account

As **a person whose work email runs on Microsoft 365, or who has an Outlook.com account**, I want **to confirm the booking my agent made by signing in with Microsoft**, so that **I don't need a Google account**.

### US-2: Confirm with Altimist ID

As **a person with an Altimist ID**, I want **to confirm with it, or create one on the way**, so that **I can use the passkey I already have**.

### US-3: Cancel with the account I booked with

As **a guest**, I want **cancelling to accept the same account I confirmed with**, so that **the provider I chose doesn't matter later**.

### US-4: Only offered what works

As **a person on the confirm page**, I want **to see only the sign-in options that are switched on and set up**, so that **I don't hit a button that can't work**.

---

## Goals & Non-Goals

**Goals**
- Microsoft and Altimist ID confirm and cancel exactly as Google does in F-002, through `confirmRequest` and `cancelMeeting`.
- The address used for the invite is one the provider stands behind (rules per provider, D3–D4).
- A provider is offered only when it's launched and its secrets are set; launching one is a config change, not a code change.
- Cost stays at £0.

**Non-Goals**
- MCP URL-mode elicitation (see Summary).
- Linking accounts: a person who signs in with Google one day and Microsoft the next counts as two people for the per-person caps. Accepted: the caps exist to bound abuse, and the daily and global caps still apply.
- Agents signing in with their own identity (F-002 P4).
- Retiring the email form (F-002 P3).
- Microsoft Graph or any scope beyond sign-in.

The answer is read from its OAuth `error` (RFC 6749 5.2, which allows a 400 or a 401 for it): `invalid_client` means rejected; `invalid_grant`, or any other OAuth error that shows the client was authenticated before the code was looked at, means ok; a network error, a timeout, a 5xx or a body that isn't an OAuth error means unknown, which changes nothing. The booking Durable Object rate-limits probes to one per provider per hour however often health is called (two calls arriving together may both probe), and health reuses the stored result in between. **Real exchanges** also count: `invalid_client` means rejected and a successful exchange means ok; anything else (`invalid_grant` from a reused or stale code, a 5xx, a timeout) changes nothing, since a visitor or an outage can cause it. **Only `invalid_client` is a rejection.** Microsoft answers an expired secret with `invalid_client` (AADSTS7000222) and a wrong or deleted one with `invalid_client` (AADSTS7000215). `unauthorized_client` covers problems with the app, the tenant or the grant type (for example AADSTS700016, app not found in the directory, and AADSTS7000112, app disabled), and can be specific to one visitor's tenant, so it must not mark the provider rejected for everyone; it is handled as any other failed exchange (Microsoft Learn, error code reference, checked 11 Nov 2026). **State:** per provider, the latest decisive result (ok or rejected, from a probe or a real exchange, whichever came last) and the time of the last probe are kept in the booking store's `health` table, so they survive a Durable Object restart. Health's `credentials` is `"rejected"` when that result is a rejection; otherwise `"expiring"` when the provider is Microsoft, Microsoft is launched and the clock is 30 days or less before `signin.microsoftSecretExpires`; otherwise `"ok"` when the result is ok; and `"unknown"` when there is no decisive result yet (say the first probe timed out). The smoke check, which the monitor runs every 6 hours, fails when a launched provider's `credentials` isn't `"ok"`; since a smoke run calls health, and health probes once the last probe is an hour old, a secret revoked between runs shows at the next run with no sign-in needed. A rejected provider keeps its button: the signal is for Patrick, and hiding the button fixes nothing. Microsoft documents lockout (smart lockout) for user passwords; we found nothing documented about locking or throttling an app's client credentials after failed requests (unverified), and one request per provider per hour is far below any published request limit. That Google and Altimist ID check the client before the code, and answer a wrong secret with `invalid_client`, is assumed from RFC 6749 and unverified; the manual checks confirm it for each provider before the probe is relied on. | Remembering: a sign-in that silently stops working when the secret lapses. The build check alone: misses a secret revoked early, and an expiry with no push in the 30 days before it. Real exchanges alone: a quiet site could run on a dead secret for weeks. ## User Flows

### Flow 1: Confirm with Microsoft or Altimist ID

1. As F-002 Flow 1 up to the confirm page.
2. The person clicks "Sign in with Microsoft" (or Altimist ID). `POST /book/confirm/microsoft` creates a `signin_tx` bound to the ticket, purpose and provider, sets the `__Host-` cookie and redirects to the provider with PKCE (S256), `state` and `nonce`.
3. The provider returns to `/book/callback/microsoft`. The site consumes `state`, exchanges the code server-side, checks the ID token as D3 (or D4) says, builds `person` and `grant` (`proof: "signin:microsoft"` or `"signin:altimist"`), and calls `confirmRequest`.
4. From here it's F-002: booked, declined or being finished.

### Flow 2: Create an Altimist ID on the way

Under the Altimist ID button, wherever it shows (the confirm page, `/book` after a time is picked, and the WebMCP popup), "No Altimist ID? Create one" opens, in a new tab (`target="_blank" rel="noopener noreferrer"`), `https://altimist.id/signup/self-service?app_id=patrickjv-com&return_to=https%3A%2F%2Fpatrickjv.com%2Fbook%2Fconfirm%3Fsigned_up%3D1` (Altimist ID's self-service contract, checked 12 Oct 2026: it requires `app_id` and a `return_to` whose origin is allow-listed for that app). The `return_to` is the same for everyone and carries no ticket. A ticket is a bearer credential (under F-002, whoever signs in on its confirm page becomes the booked person), and anything in `return_to` reaches Altimist ID's logs and analytics. The confirm page's `Referrer-Policy: same-origin` already keeps its own URL out of the `Referer`. After sign-up, Altimist ID returns the new tab to `/book/confirm?signed_up=1`, which shows no form and says, in words that fit all three starting points: "Your Altimist ID is ready. Go back to the tab where you were booking and choose Sign in with Altimist ID. If that tab has gone, open the link from your assistant again, or start again at patrickjv.com/book." The last sentence is for in-app browsers and the WebMCP popup, where the first tab may have closed or may not be reachable. The confirm page is still open in the first tab with its ticket (and any trial pair) unchanged, and `/book` still has the chosen time (its request is created only on the first sign-in click), so nothing has to be carried across. If the ticket has expired by then, that tab's sign-in shows F-002's "expired" page. `signed_up=1` only has meaning without a ticket: with `t=` present, the parameter is ignored and the confirm page renders for that ticket as it would without it (no link of ours ever produces that URL).

### Flow 3: Cancel

As F-002 Flow 3: a sign-in whose `provider` and `subject` match the guest cancels. A cancel link offers **only the booking's own provider** ("You booked with Microsoft. Sign in with Microsoft to cancel."), because no other account can cancel it. If that provider isn't ready, the page says so and points to the "Booked" email's cancel link, as the start-refusal rule below describes. A sign-in with the right provider but a different account changes nothing ("This booking belongs to someone else").

## Acceptance Criteria

### Functional

- [ ] **(D2)** Sign-in start and callback work for `google`, `microsoft` and `altimist` through one shared implementation. An unknown provider in the path is 404. A transaction started for one provider and completed on another provider's callback is refused: `state` is consumed (as F-002 consumes it before any other check), so that transaction is spent, while the request, its ticket and any booking are unchanged and the person can start again (tested for each pair).
- [ ] **Shared token rules, all providers, applied by the one shared check (D2):** `aud` must be a string equal to our client ID for that provider (an array is refused, as Google's shipped check already does, so Google's behaviour doesn't change). `iss` must equal the provider's issuer exactly; each provider supplies only the expected value (Google: `https://accounts.google.com` or `accounts.google.com`; Microsoft: D3's tenant issuer, built from `tid`, so a `tid` that isn't a GUID gives no issuer and is refused; Altimist ID: `https://altimist.id`). `exp` and `iat` must be numbers, `exp` in the future and `iat` within 5 minutes. `nbf`, if present, must be a number no more than 5 minutes in the future (the same leeway as `iat`, for clock skew). `nonce` must equal the transaction's. **Required claims, each a non-empty string:** Google: `sub` and `email` (as F-002); Microsoft: `tid` and `oid` (an `email` that is missing, not a string, empty or without `@` is handled by D3's address rule: refused with the address message, not as a malformed token); Altimist ID: `sub` and `email`. Each failure is refused with the request, its ticket and any booking unchanged; `state` is consumed, so that sign-in transaction is spent, as in F-002 (tested per provider, including empty strings, wrong types, a wrong issuer, an `nbf` 4 minutes ahead, which passes, and one 6 minutes ahead, which is refused). **Provider-specific checks** come after the shared ones and are only those in the next criteria: Microsoft's `tid` format, `ver` and address rule; Google's and Altimist ID's `email` and `email_verified` rules.

## Edge Cases

- **Microsoft "needs admin approval":** should be rare after publisher verification; if it happens, the person signs in another way. Nothing on our side can fix an organisation's consent policy.
- **Microsoft guest accounts:** `/common` signs people in to their home tenant, so `tid` is their home tenant; the key is stable.
- **A personal Microsoft account without an `email` claim:** refused as above (can happen for phone-number-only accounts).
- **Altimist ID sign-up takes longer than the ticket lasts:** the confirm page shows "expired", with F-002's advice to ask again.
- **A Microsoft secret expires or is revoked early:** every code exchange and probe gets `invalid_client`; health's `credentials` turns `"rejected"` at the first sign-in or the next probe, whichever comes first, and the next monitor smoke fails (D6). The button stays.
- **One visitor's tenant blocks the app** (`unauthorized_client`, for example the app disabled in that tenant): that sign-in fails as any failed exchange does; `credentials` is unchanged, because the problem is that tenant's, not our secret's (D6).
- **A provider goes down mid-flow:** the callback's code exchange fails; F-002's rule applies (the transaction is spent, the ticket isn't).
