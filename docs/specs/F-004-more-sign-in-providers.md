# Feature Spec: Sign in with Microsoft or Altimist ID to confirm

> **Purpose:** F-002 P2. Let people confirm (and cancel) a booking by signing in with Microsoft or Altimist ID as well as Google, through F-002's existing confirm page and booking core.
> **Update when:** Requirements shift, acceptance criteria change, or scope moves during the build.

## Summary

F-002 made signing in with Google the way a booking is confirmed. People without a Google account, or whose company runs on Microsoft 365, are left with `/book`'s email form, and their agents can't book for them at all. F-004 adds **Sign in with Microsoft** (work, school and personal accounts) and **Sign in with Altimist ID** as more buttons on the same confirm page. Each provider's only job is to produce F-002's `person` and `grant`; the booking core, caps, failure rules and cancellation stay as they are.

MCP URL-mode elicitation, which F-002 listed under P2, is **out of scope**: the protocol changed it in 2026-07-28 and the major clients don't reliably support it yet (research, 9 Oct 2026). The confirm link stays in the tool result.

---

## User Stories

### US-1: Confirm with my Microsoft account

As **a person whose work email runs on Microsoft 365, or who has an Outlook.com account**, I want **to confirm the booking my agent made by signing in with Microsoft**, so that **I don't need a Google account**.

### US-2: Confirm with Altimist ID

As **a person with an Altimist ID**, I want **to confirm with it, or create one on the way**, so that **I can use the passkey I already have**.

### US-3: Cancel with the account I booked with

As **a guest**, I want **cancelling to accept the same account I confirmed with**, so that **the provider I chose doesn't matter later**.

### US-4: Only offered what works

As **a person on the confirm page**, I want **to see only the sign-in options that are switched on and set up**, so that **I don't hit a button that can't work**.

---

## Goals & Non-Goals

**Goals**
- Microsoft and Altimist ID confirm and cancel exactly as Google does in F-002, through `confirmRequest` and `cancelMeeting`.
- The address used for the invite is one the provider stands behind (rules per provider, D3–D4).
- A provider is offered only when it's launched and its secrets are set; launching one is a config change, not a code change.
- Cost stays at £0.

**Non-Goals**
- MCP URL-mode elicitation (see Summary).
- Linking accounts: a person who signs in with Google one day and Microsoft the next counts as two people for the per-person caps. Accepted: the caps exist to bound abuse, and the daily and global caps still apply.
- Agents signing in with their own identity (F-002 P4).
- Retiring the email form (F-002 P3).
- Microsoft Graph or any scope beyond sign-in.

The build check alone: misses a secret revoked early, and an expiry with no push in the 30 days before it. |
| D7 | **Launched in config, offered when ready.** `booking.json` lists the **launched** providers (`signin.providers`, default `["google"]`). **Validation** (build and Worker start, as for the rest of `booking.json`): the list must include `"google"`, contain only `google`, `microsoft` and `altimist`, and have no duplicates; anything else fails the build (tested for each case, including `["microsoft","google"]`, which passes). They get no button and appear in no general copy or `signin_providers`. **Trial is owner-only.** A trial view needs the pair `&try=<provider>&trial=<mark>`, where the mark is the first 16 bytes of HMAC-SHA256 over `<provider>:<ticket>` keyed with the Worker secret `SIGNIN_TRIAL_KEY`, base64url-encoded. A mark therefore works for one provider on one ticket, and only the holder of the key can make one (`npm run trial-link -- <provider> <confirm URL>`, with the key in the environment). Marks are compared in constant time. The trial button's form carries both values, and `POST /book/confirm/<provider>` for a trial provider starts only when it is ready and the request carries a valid mark for that ticket; without one it is refused as a provider that isn't launched (the 303 in Functional). With `SIGNIN_TRIAL_KEY` unset there is no trial view or start at all. Cancelling a booking made with a trial provider needs no mark, because only that booking's own account can cancel it. **Exceptions, where the person is already using that provider:** the confirm page opened with a valid trial pair shows that provider's button (and, for Altimist ID, the "Create one" link) in its place in the fixed order, so the manual checks exercise the real page; a booking made with a trial provider is named as such on its cancel page and in `cancel_booking`'s `next_step`; failure messages about it name it; and the privacy page names every enabled provider because a trial sign-in still sends data to it. `try=` with a missing or wrong mark, or for a provider that isn't on trial, is ignored (tested). A provider can't be in both lists (build fails). Launched and trial providers together are the **enabled** ones. The list's order doesn't matter: providers are always shown and named in the fixed order Google, Microsoft, Altimist ID. The static copy (the booking guide everywhere it's published, `/book.md`, `llms.txt`) names the launched providers, built from that list, so a short outage never changes published text. `book_meeting`'s `next_step` is written per request, so it names only the launched providers that are ready when the request is made, which are the ones its confirm page will offer. **Callbacks:** a transaction started while a provider was ready may complete if, at the callback, the provider is still enabled (launched or on trial) and its secrets are still set (the code exchange itself shows whether it's reachable); otherwise the callback is refused, `state` is consumed, and the request and ticket are unchanged (tested: secrets removed mid-flow; provider removed from both lists mid-flow; a trial provider's sign-in completes and books, and cancels). At runtime a launched provider is **ready** when its client ID and secret are set, which is exactly how F-002 gates Google today (request admission and sign-in start check the secrets, not reachability), and buttons appear only for ready ones. Reachability of each provider's discovery document is reported by health and checked by the smoke test, as F-002 does for Google, but doesn't hide buttons or refuse requests: an unreachable provider shows up as a failed code exchange, handled as F-002 handles it. The Worker-rendered surfaces (the confirm page, `initialize`, `get_booking_guide`) read the same `booking.json`, so the guide text is identical everywhere. `/book` and the homepage's WebMCP are static pages, so they get the ready list from `GET /api/booking/types`, which gains `signin_providers: [...]`. Launching Microsoft is a `booking.json` change plus the secrets. **Both Workers must deploy on a `booking.json` change:** `patrickjv-mcp`'s Workers Builds watch paths (set in the Cloudflare dashboard, listed in `docs/06-operations.md`) gain `booking.json`, which they lack today, so a config-only push redeploys it too. Health reports each enabled provider's readiness (secrets set), reachability and credentials (D6). **Reachability:** health fetches each enabled provider's discovery document itself when its cached result is a minute old or more, or absent (after the booking Durable Object restarts), and otherwise reuses the cached result. `reachable` is `false` only when that fetch failed or timed out (20 seconds), so an idle site never reads as unreachable. The cache is held in the booking Durable Object, of which there is one, so however often health is called, each provider's discovery document is fetched about once a minute at most (two calls arriving together may both fetch), and health itself sits behind the MCP endpoint's per-IP rate limits. `signinReady` keeps its F-002 meaning (Google). The smoke check requires every launched provider to be ready and reachable, with `credentials: "ok"`. | Switching on by secrets alone: the static copy couldn't know, and setting a secret would launch a provider with no deploy or review. A code flag per provider: needs code changes. Health reading a cached result only: an idle site would show providers as unreachable. |
| D8 | **The site may name "Altimist ID", and nothing else from Altimist** (decided with Patrick, 12 Oct 2026). The two paths start with `/`, so nothing before them can join onto "altimist"; they are bounded on the right only. ## User Flows

### Flow 1: Confirm with Microsoft or Altimist ID

1. As F-002 Flow 1 up to the confirm page.
2. The person clicks "Sign in with Microsoft" (or Altimist ID). `POST /book/confirm/microsoft` creates a `signin_tx` bound to the ticket, purpose and provider, sets the `__Host-` cookie and redirects to the provider with PKCE (S256), `state` and `nonce`.
3. The provider returns to `/book/callback/microsoft`. The site consumes `state`, exchanges the code server-side, checks the ID token as D3 (or D4) says, builds `person` and `grant` (`proof: "signin:microsoft"` or `"signin:altimist"`), and calls `confirmRequest`.
4. From here it's F-002: booked, declined or being finished.

### Flow 2: Create an Altimist ID on the way

Under the Altimist ID button, "No Altimist ID? Create one" opens, in a new tab (`target="_blank" rel="noopener noreferrer"`), `https://altimist.id/signup/self-service?app_id=patrickjv-com&return_to=https%3A%2F%2Fpatrickjv.com%2Fbook%2Fconfirm%3Fsigned_up%3D1` (Altimist ID's self-service contract, checked 12 Oct 2026: it requires `app_id` and a `return_to` whose origin is allow-listed for that app). The `return_to` is the same for everyone and carries no ticket. A ticket is a bearer credential (under F-002, whoever signs in on its confirm page becomes the booked person), and anything in `return_to` reaches Altimist ID's logs and analytics. The confirm page's `Referrer-Policy: same-origin` already keeps its own URL out of the `Referer`. After sign-up, Altimist ID returns the new tab to `/book/confirm?signed_up=1`, which says "Your Altimist ID is ready. Go back to the tab with your booking link and choose Sign in with Altimist ID." The confirm page is still open in the first tab with its ticket (and any trial pair) unchanged, so nothing has to be carried across. If the ticket has expired by then, that tab's sign-in shows F-002's "expired" page.

### Flow 3: Cancel

As F-002 Flow 3: a sign-in whose `provider` and `subject` match the guest cancels. A cancel link offers **only the booking's own provider** ("You booked with Microsoft. Sign in with Microsoft to cancel."), because no other account can cancel it. If that provider isn't ready, the page says so and points to the "Booked" email's cancel link, as the start-refusal rule below describes. A sign-in with the right provider but a different account changes nothing ("This booking belongs to someone else").

## Acceptance Criteria

### Functional

- [ ] **(D2)** Sign-in start and callback work for `google`, `microsoft` and `altimist` through one shared implementation. An unknown provider in the path is 404. A transaction started for one provider and completed on another provider's callback is refused: `state` is consumed (as F-002 consumes it before any other check), so that transaction is spent, while the request, its ticket and any booking are unchanged and the person can start again (tested for each pair).
- [ ] **Shared token rules, all providers, applied by the one shared check (D2):** `aud` must be a string equal to our client ID for that provider (an array is refused, as Google's shipped check already does, so Google's behaviour doesn't change). `iss` must equal the provider's issuer exactly; each provider supplies only the expected value (Google: `https://accounts.google.com` or `accounts.google.com`; Microsoft: D3's tenant issuer, built from `tid`, so a `tid` that isn't a GUID gives no issuer and is refused; Altimist ID: `https://altimist.id`). `exp` and `iat` must be numbers, `exp` in the future and `iat` within 5 minutes. `nbf`, if present, must be a number not in the future. `nonce` must equal the transaction's. **Required claims, each a non-empty string:** Google: `sub` and `email` (as F-002); Microsoft: `tid` and `oid` (an `email` that is missing, not a string, empty or without `@` is handled by D3's address rule: refused with the address message, not as a malformed token); Altimist ID: `sub` and `email`. A claim the provider doesn't define (for example `oid` from Google) is never required. Each failure is refused with the request, its ticket and any booking unchanged; `state` is consumed, so that sign-in transaction is spent, as in F-002 (tested per provider, including empty strings, wrong types, a wrong issuer and an `nbf` in the future). **Provider-specific checks** come after the shared ones and are only those in the next criteria: Microsoft's `tid` format, `ver` and address rule; Google's and Altimist ID's `email` and `email_verified` rules.
- [ ] **(US-1, D3)** Microsoft ID-token checks, each tested with a fake Microsoft: the shared rules, with `iss` exactly `https://login.microsoftonline.com/<tid>/v2.0`; then, specific to Microsoft, `tid` is a GUID, `ver` is `2.0` and `oid` is present. Refused: any of these failing; an `iss` for a different tenant than `tid`; a `tid` that isn't a GUID.
- [ ] **(US-1, D3)** Microsoft address rule (tested): a work account with `email` and `xms_edov: true` books; a personal account (`tid` 9188040d-…) with `email` books with or without `xms_edov`; a work account with `email` but `xms_edov` false or missing, or no `email` at all, is refused with nothing changed and the request left open, and the page says, when booking, "Microsoft couldn't confirm this address belongs to you. Sign in another way, or book at patrickjv.com/book with email instead.", and when cancelling, "Microsoft couldn't confirm this address belongs to you. Sign in with the account you booked with, or use the cancel link in your 'Booked' email." with the meeting left booked (both tested). `upn` and `preferred_username` are never used as the address.
- [ ] **(US-1, D3)** The person is `{provider: "microsoft", subject: "<tid>:<oid>", email: <email>, display_name: <name claim, else the part before @>}`. Two sign-ins with the same `tid` and `oid` but different addresses are the same person for the caps (tested).
- [ ] **(US-2, D4)** Altimist ID ID-token checks (tested with a fake Altimist ID): the shared rules above, with `iss` exactly `https://altimist.id`; then, specific to Altimist ID, `email` containing `@`. If `email_verified` is present it must be `true`. The name is `given_name` + `family_name` when either is non-empty, else the part of the address before `@`. The person is `{provider: "altimist", subject: <sub>, …}`.
- [ ] **(US-2)** The "Create one" link is exactly `https://altimist.id/signup/self-service?app_id=patrickjv-com&return_to=https%3A%2F%2Fpatrickjv.com%2Fbook%2Fconfirm%3Fsigned_up%3D1`, opens in a new tab with `rel="noopener noreferrer"`, and appears only while the Altimist ID button does. The link contains neither the ticket, nor its hash, nor a trial mark (tested by rendering the confirm page for a known ticket, plain and with a trial pair, and searching the link for each). `GET /book/confirm?signed_up=1` with no ticket returns 200 with Flow 2's "Your Altimist ID is ready" text and no form (tested). The round trip through Altimist ID is a manual check.
- [ ] **(US-3)** `cancelMeeting` accepts a sign-in only when `provider` and `subject` both match the guest (tested: same provider and subject cancels; same email through a different provider changes nothing; same provider, different subject changes nothing). The cancel page names the provider the booking was made with. `cancel_booking`'s `next_step` names the booking's provider (tested for each provider).
- [ ] **(US-4, D7)** The confirm page, `/book` and the WebMCP popup offer exactly the launched providers that are ready (secrets set, as F-002 gates Google). The one exception is the confirm page opened with a valid trial pair, which also shows that trial provider if it is ready (D7); `/book` and the WebMCP popup never show a trial provider. Otherwise a provider that isn't launched, or is launched but not ready, gets no button. **Start responses:** a path that isn't one of `google`, `microsoft`, `altimist` is 404; a known provider that isn't launched (and isn't on trial) or isn't ready, with a valid ticket, is the 303 described below; a provider on trial and ready starts normally only with a valid trial mark for that ticket, and otherwise is the 303; an invalid, used or expired ticket is handled as in F-002, whatever the provider (tested for each). `GET /api/booking/types` returns `signin_providers` (the ready ones, in order) and `/book` and the WebMCP prompt render buttons from it (tested). Health adds `providers: {google, microsoft, altimist}`: for an enabled provider (launched or on trial) `{ready: <secrets set>, reachable: <health's discovery fetch, or one cached for under a minute, succeeded (D7)>, credentials: "ok" | "expiring" | "rejected" (D6)}`, otherwise `"off"`. The smoke check requires `ready` and `reachable` true and `credentials` `"ok"` for every launched provider. `signinReady` keeps its F-002 meaning. Tested: two health calls within a minute make one discovery fetch per provider, a call after a minute makes another, and the first call after the cache is empty fetches. **Freshness on static pages:** `/book` and the homepage fetch `signin_providers` when the person reaches the sign-in choice (after picking a time), not at page load. **A start refused because its known provider isn't ready** (launched but not ready, or not launched), with a valid ticket, redirects (303) to that request's own confirm page (`/book/confirm?t=…`), which says what to do for its purpose: **booking**, with other providers ready: "That sign-in isn't available just now. Choose another." above the ready buttons; **booking**, with none ready: "Sign-in isn't available just now. Try again in a few minutes, or book at patrickjv.com/book with email instead."; **cancelling** (only the booking's own provider is ever offered): "<booking's provider> sign-in isn't available just now. Try again in a few minutes, or use the cancel link in your 'Booked' email.", with no button (each tested, including a booking's provider unready while others are ready). Nothing new is created: the same request and ticket are reused, no request allowance is taken, and no sign-in attempt is counted. On `/book` the request is created once, on the first sign-in click, and the page keeps its `confirm_url`; when a start is refused, the WebMCP popup lands on the same confirm page (an accepted start goes straight to the provider, as today). Tested: a provider goes unready between rendering the choices and submitting, on `/book`, on the confirm page and in the WebMCP popup; a provider recovers after the page loads.
- [ ] **(D7) Request admission:** `book_meeting` and `POST /api/booking/request` accept a request when at least one launched provider is ready, and refuse with F-001's `503` and a `next_step` when none is (today's Google-only check generalised). ## Setup (manual)

**Microsoft** (in an Entra tenant Patrick personally controls, not a work tenant; publisher verification needs an Entra tenant and a Microsoft AI Cloud Partner Program account):
1. App registration "patrickjv.com", supported account types "Any Microsoft Entra directory and personal Microsoft accounts", web redirect URI `https://patrickjv.com/book/callback/microsoft`.
2. Token configuration: optional ID-token claims `email` and `xms_edov`.
3. Set `authenticationBehaviors.removeUnverifiedEmailClaim = true` (Microsoft Graph PATCH on the application).

## Edge Cases

- **Microsoft "needs admin approval":** should be rare after publisher verification; if it happens, the person signs in another way. Nothing on our side can fix an organisation's consent policy.
- **Microsoft guest accounts:** `/common` signs people in to their home tenant, so `tid` is their home tenant; the key is stable.
- **A personal Microsoft account without an `email` claim:** refused as above (can happen for phone-number-only accounts).
- **Altimist ID sign-up takes longer than the ticket lasts:** the confirm page shows "expired", with F-002's advice to ask again.
- **A Microsoft secret expires or is revoked early:** every code exchange gets `invalid_client`; health's `credentials` turns `"rejected"` at the first one and the next monitor smoke fails (D6). The button stays.
- **A provider goes down mid-flow:** the callback's code exchange fails; F-002's rule applies (the transaction is spent, the ticket isn't).
