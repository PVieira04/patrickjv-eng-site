## Summary

The research agent is a private project: a LangGraph agent, built on LangChain, that answers a researcher's plain-English question about time-series data by writing a plan, waiting for approval, running Python in a sandboxed MCP server, having a second model check the work for known traps, and writing a report. An eval scores it against a seeded synthetic dataset with known answers and planted traps.

This spec adds two static pages to patrickjv.com, served as assets by the existing `patrickjv-eng-site` Worker and built by `build.mjs` like `/writing/`:

- **`/projects/`**, an index of projects with a showcase (one entry for now);
- **`/projects/research-agent`**, the showcase: what the project is, its architecture, the eval scorecard and recorded runs from published synthetic data, and how it was built.

Each published run gets its own page, `/projects/research-agent/runs/<run_id>`, with Markdown and JSON twins. The code stays private. The only things that cross from the private repository are exports of `research publish <id>` (`report.json`, `report.md`, figures) and published eval scorecards, after the owner has read them, recorded by file hash in a manifest the build enforces. Until Databento confirms its licence terms, the build refuses any report that isn't on the synthetic dataset.

LangChain and LangGraph appear in the title, meta description and JSON-LD keywords, not in the URL.

## User Stories

### US-1: Recruiter scanning for skills

As **a recruiter** who searched for LangChain, LangGraph or AI agent experience, I want **a page whose title and first paragraph say plainly what was built and with what**, so that **I can match it to a role in under a minute without reading code**.

### US-2: Hiring engineer checking depth

As **a hiring engineer**, I want **the architecture, the measured eval results with their denominators, and full recorded runs (plan, approval, analysis, the critic catching a planted trap, the final report)**, so that **I can judge the engineering without access to the private code**.

### US-3: A visitor's agent

As **an AI agent acting for a visitor**, I want **the showcase and every published run as clean Markdown and JSON, linked from `llms.txt`, `index.md` and the sitemap**, so that **I can answer "what has Patrick built with LangGraph?" from the source, without scraping HTML**.

### US-4: Owner publishing safely

As **the owner**, I want **only exports I have read, byte for byte, to reach the public repository and site, and real-data results refused until the licence question is answered**, so that **nothing private, licensed or unchecked is published by accident**.

## Page content

### `/projects/`

Heading "Projects", one sentence of intro, then one entry per project: title, one-line summary, the stack as text (for example "Python · LangGraph · LangChain · MCP"), and a link. One entry in this spec: the research agent. Same layout as `/writing/`'s post list.

### `/projects/research-agent`

Sections, in order (headings are working titles; final copy is approved by the owner):

1. **Heading and lead.** `<h1>`: "Research agent". Lead paragraph: what it does, in one or two sentences, naming LangGraph, LangChain and MCP. A line: "Private code, available on request" with a `mailto:` to the approved address.
2. **What it does.** A researcher asks a question about their own time-series data; the agent plans, waits for approval, analyses in a sandbox, has a critic check the work, and writes a report with the code, the numbers and any problems it couldn't resolve. The worked example is NQ futures 1-minute bars; **every result on this page is on a seeded synthetic dataset**, and the page says so above the scorecard and on every run.
3. **Architecture.** The inline SVG diagram (D4) and short text for each part:
   - **The graph** (LangGraph): plan → human approval (interrupt) → analyse loop → critic → report; tool and token caps; checkpointing and resume.
   - **The research MCP server**: three tools, used both by the graph and by Claude Code on its own; access levels and dataset visibility.
   - **The sandbox**: generated code runs with no network, no secrets, read-only data and hard limits (bubblewrap, cgroup memory limit, seccomp filter). Described at that level only; no host details.
   - **The eval**: ten questions on synthetic data with planted effects and traps, k repeats, scored for answer accuracy, trap recall and critic precision, with paired comparison between versions.
   - **The Claude Code harness**: an interim harness with no API keys (a `/research` skill, analyst and critic subagents, a permission rule on code execution).
4. **Eval scorecard.** From the newest published scorecard (manifest order decides if dates tie): date, k, harness and models, synthetic seed; a table per question with correct / n, trap recall x / n, critic precision x / n; the aggregate score with its standard error. Counts are always shown with their denominators; a measure with n = 0 shows "n/a", not 0 % or 100 %. If more than one scorecard is published, older ones are listed by date and link to their own section on the same page, not compared (comparison text belongs to the eval, not the page).
5. **Recorded runs.** One card per published run: the question, the harness (`langgraph` shown as "LangGraph agent", `claude-code` as "Claude Code harness"), the status, the review outcome, the role from the manifest, and a link to the run page. Runs with a role are shown first, in the order `trap_caught`, `rejected_plan`, `clean_pass`.
6. **How it was built.** Spec-first: every part had a written spec with testable acceptance criteria before code; specs and code went through several rounds of adversarial review by a second model, findings fixed and recorded; tests before implementation; the sandbox's threat model written first. Generic description only: no employer, client, team or internal tool names.
7. **Footer**, as the writing pages.

### `/projects/research-agent/runs/<run_id>`

Header: the question, date (`finished_at`, UTC, as `YYYY-MM-DD`), harness, models, status, review outcome, dataset name with "synthetic". Then the rendered `report.md` (D5), with its figures inline as `<img>` with `width` and `height` from the PNG header, alt text from the manifest, `loading="lazy"` for all but the first. Then links: "Markdown" (`.md`), "JSON" (`.json`), back to the showcase.

### Copy rules

- The employer denylist applies to every new page and twin, including the exported report text (it's model-written; a slip must fail the build, not ship).
- No home paths, host names, private repository paths or secrets anywhere in the output (see Functional criteria for the scan).
- Public copy is approved by the owner before launch.

## The publish boundary

1. In the private repository, `research publish <run_id>` checks the run (as its own spec defines) and writes an export directory: `report.json`, `report.md`, and the figures named in `report.json` → `figures`.
2. The owner reads every file in the export: the report text, the figures, and the JSON.
3. The owner copies the export to `projects/research-agent/runs/<run_id>/` in this repository, flattening figure paths to their base names (the figure names in `report.json` are rewritten by the build at render time, not in the file, so the JSON hash stays the one the owner checked), and runs `node build.mjs --record <run_id>` (new), which adds the run to `published.json` with today's date, each file's sha256, and an empty alt text for each figure.
4. The owner writes each figure's alt text and the optional role in `published.json`. The build refuses an empty alt text.
5. A PR to `main`. The diff is the second look: the PR shows exactly the bytes that will be served.

The same flow applies to scorecards, under `scorecards/<eval_id>/scorecard.json`, recorded by `--record-scorecard <eval_id>`. That needs `research publish` to export a scorecard (open question 1).

`--record` writes only the manifest; it never copies, fetches or rewrites the exported files.

## CSP and third parties

- One exact `_headers` rule per new HTML path (both the clean URL and the `.html` name, as for writing posts): `default-src 'none'; img-src 'self'; font-src 'self'; style-src 'sha256-…'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'; upgrade-insecure-requests`. **No `script-src`**: the pages have no script.
- Markdown and JSON twins: baseline CSP and explicit `Content-Type` with `charset=utf-8` (`text/markdown`, `application/json`).
- Figures: one exact rule per file with the image cache policy (one day) and baseline CSP, as for the site's images. No wildcard rules (the 6 Oct incident).
- The build's inline-code guards apply to every new page: exactly one inline `<style>`, no executable script, no `style="…"` or `on…` attribute. This includes the inlined SVG: it must use classes styled by the page's one `<style>`, and may not contain `<script>`, `<foreignObject>`, `on…` attributes, `style` attributes or any `href` that isn't a same-page fragment.
- Zero third-party requests: no external fonts, images, scripts, embeds or analytics.

## Edge cases

- **No runs yet.** Before launch the showcase builds with "No published runs yet" in place of the runs list and no scorecard section; after launch this can't happen (D8).
- **Only Claude Code harness runs published.** The title still names LangGraph because the project is built on it, but every run shows its harness, so nothing implies a LangGraph run that wasn't one. See open question 2.
- **Run statuses.** `completed`, `rejected`, `capped` and `failed` are all accepted and shown with their status; a `rejected` run shows the plan and the rejection reason, which is how the approval step is demonstrated.
- **`review.outcome` `not_passed` with open issues.** Shown as is, with the open issues listed; the page doesn't hide a critic's unresolved finding.
- **Run id characters.** Run ids are used in URLs and file names. The build accepts only the report schema's pattern, `^[0-9]{8}T[0-9]{6}Z-[0-9a-f]{6}$` (for example `20261111T143000Z-a1b2c3`), which is URL-safe as is.
- **Figure names.** Base names must be unique within a run after flattening; a collision fails the build.
- **Very long reports.** No truncation; the HTML budget (30 KB gzip) fails the build if a report is too long, and the owner decides whether to publish it.
- **Question text with Markdown or HTML.** Rendered as text everywhere (titles, cards, JSON-LD), never as markup.
- **A run unpublished later.** Removing it from the manifest and the directory removes all its outputs, its sitemap entries and its smoke checks in one build; the URL then returns the 404 page. Search engines drop it in time; no redirect.
- **Scorecard from an older report schema.** A `scorecard_version` major other than 1 fails the build.
- **`/projects/research-agent` and `/projects/research-agent/` coexisting** (a file `research-agent.html` next to a directory `research-agent/`): the asset server's trailing-slash handling must serve the HTML at the clean URL in production, not only under `wrangler dev`. Checked by smoke after the first deploy; if it doesn't hold, runs move to `/projects/research-agent-runs/<id>` (see open question 5).
- **Clock and dates.** Displayed dates come from the files (`finished_at`, the manifest's checked date), never the build machine's clock, so `--check` stays deterministic.

## Open questions

1. **Scorecard export.** The research-agent spec says `research publish <id>` exports `report.json`, `report.md` and figures. The scorecard is a separate file (`scorecard.json`, including the private repository's git commit and prompt hashes). Should `research publish` gain a scorecard export, and may the commit and prompt hashes be published, or should the export drop them?
2. **Launch with which harness?** If the Claude Code harness ships before the LangGraph graph, may the page launch with only `claude-code` runs and a scorecard from that harness, or does launch wait for at least one LangGraph run?
3. **Which runs to feature.** Which three to five synthetic runs make the set: at least one where the critic catches a planted trap and one rejected plan, as the research-agent spec lists?
4. **Homepage entry point.** Side-project entry only (this spec), or also a "Projects" link in the header nav (which must keep its 24 px tap targets)?
5. **URL fallback.** If the clean-URL check in "Edge cases" fails in production, is `/projects/research-agent-runs/<id>` acceptable, or would you rather keep run pages as sections of the showcase page?
6. **"Code available on request".** Is a `mailto:` line enough, or should it point to `/book` for a call?
7. **Real data.** When Databento answers the four questions in the research-agent spec, the gate in D6 opens by a spec change here. Not a question for this build; listed so the dependency isn't lost.
