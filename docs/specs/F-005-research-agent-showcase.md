## Summary

The research agent is a private project: a LangGraph agent, built on LangChain, that answers a researcher's plain-English question about time-series data by writing a plan, waiting for approval, running Python in a sandboxed MCP server, having a second model check the work for known traps, and writing a report. An eval scores it against a seeded synthetic dataset with known answers and planted traps.

This spec adds static pages to patrickjv.com, served as assets by the existing `patrickjv-eng-site` Worker and generated by `build.mjs` like `/writing/`:

- **`/projects/`**, an index of projects with a showcase (one entry for now);
- **`/projects/research-agent`**, the showcase: what the project is, its architecture, the eval scorecard and recorded runs from published synthetic data, and how it was built;
- **`/projects/research-agent/runs/<run_id>/`**, one page per published run, with the run's `report.md` and `report.json` beside it.

The code stays private. The only things that cross from the private repository are `research publish` exports that the owner has read, recorded by file hash in a manifest the build enforces. Committing an export to this public repository publishes it: the owner's read is the last check before it is public, and `--record` runs every build check before it writes anything. The build owns everything under `public/projects/`: what it doesn't generate from the manifest is deleted, and `--check` fails on it. Until Databento confirms its licence terms, the build refuses anything that isn't on the synthetic dataset.

LangChain and LangGraph appear in the title, meta description, lead paragraph and JSON-LD keywords, not in the URL.

## User Stories

### US-1: Recruiter scanning for skills

As **a recruiter** who searched for LangChain, LangGraph or AI agent experience, I want **a page whose title and first paragraph say plainly what was built and with what**, so that **I can match it to a role in under a minute without reading code**.

### US-2: Hiring engineer checking depth

As **a hiring engineer**, I want **the architecture, the measured eval results with their denominators, and full recorded runs (plan, approval, analysis, the critic catching a planted trap, the final report)**, so that **I can judge the engineering without access to the private code**.

### US-3: A visitor's agent

As **an AI agent acting for a visitor**, I want **the index, the showcase and every published run as clean Markdown, and every run's report as JSON, linked from `llms.txt`, `index.md` and the sitemap**, so that **I can answer "what has Patrick built with LangGraph?" from the source, without scraping HTML**.

### US-4: Owner publishing safely

As **the owner**, I want **only exports I have read, byte for byte, to be committed and served, every automated check to run before anything is written to this public repository, unpublishing to remove a run from the site (git history keeps it), and real-data results refused until the licence question is answered**, so that **nothing private, licensed or unchecked is published by accident**.

## Goals & Non-Goals

**Goals**
- Static pages with no script, generated by the build, with the writing pages' look (IBM Plex, palette, light and dark).
- Every served file under `public/projects/` is either generated from source or a byte copy of a manifest-listed, hash-checked export file; nothing else survives a build.
- Synthetic data only, enforced by the build and by `--record`, until a later spec change opens the real-data gate.
- The site's existing guarantees hold on every new page: per-path CSP, no third-party requests, the employer denylist, "deployed = repo" smoke checks, Lighthouse 100 for performance, accessibility and best practices.
- Cost stays at £0: static assets only, no new Worker, no R2.

**Non-Goals**
- **F-003 in the research-agent index** (MCP tools `list_research` and `get_research_report` on the site's MCP server, and the later live research Worker): a separate spec. This page uses no MCP or WebMCP tool and adds none.
- A live demo, any execution on the website, or any model spend.
- Publishing the research-agent code. The page says "Code available on request" and links to `/book`.
- **Real-data (Databento) results.** When Databento answers the four questions in the research-agent spec, opening the D6 gate is a change to this spec with the answer attached.
- **The generator's constants** (planted effect sizes, trap parameters) are not published; reports may state measured estimates.
- A general "projects" CMS. Kaizen Kingdom and the marine-weather agent stay as side projects on the homepage.
- Changes to the homepage nav.
- Comparing scorecards on the page; only the newest is published.

## Export contract

This is the consumer's contract: what this site accepts. Anything else is refused by `--record` and by the build.

### Run

`research publish <run_id>` (F-001e) writes an export folder, outside this repository, containing exactly:

- `report.json`, byte-identical to the run's and valid against `schemas/report.v1.json` (major version 1), with `run_id` equal to the export's `id`;
- `report.md`, byte-identical to the run's, with no image syntax;
- each file named in `report.json` → `figures`, at its run-relative path (`calls/<N>/out/<name>.png`), and no other figure;
- `export.json`, the hash list.

`export.json`, as F-001e defines it:

```json
{
  "export_version": "1.0.0",
  "kind": "run",
  "id": "20261111T143000Z-a1b2c3",
  "tool": { "name": "research-agent", "version": "0.1.0" },
  "exported_at": "2026-11-11T15:04:05Z",
  "files": [
    { "path": "calls/3/out/vol_by_minute.png", "sha256": "…", "bytes": 48213 },
    { "path": "report.json", "sha256": "…", "bytes": 9120 },
    { "path": "report.md", "sha256": "…", "bytes": 6311 }
  ]
}
```

What the site accepts: `export_version` major 1; `kind` `run` (or `scorecard`, below); `id` matching the kind's pattern; `tool.name` `research-agent`; `exported_at` UTC with `Z`; `files` sorted by path, each path unique, listing every file in the folder except `export.json` and nothing else, each with a 64-hex `sha256` and an integer `bytes` that both match the file. **Every entry in the export folder must be a regular file** (checked with `lstat`; a symlink, directory where a file is expected, FIFO or device is refused), and **each file is read once**: the same Buffer is hashed, checked and copied. **The export digest** is the sha256 of the `export.json` file's bytes, which F-001e prints at the end of its owner checklist; the owner passes it to `--record` as `--expect`, which ties the folder being recorded to the one the owner read. `export.json` is never committed; the manifest records the digest and what `export.json` said.

Patterns and limits: `run_id` `^[0-9]{8}T[0-9]{6}Z-[0-9a-f]{6}$`; figure path `^calls/[1-9][0-9]{0,3}/out/[A-Za-z0-9_-][A-Za-z0-9._-]{0,55}\.png$`; at most 20 figures; each figure at most 200 KB (204,800 bytes); at most 1 MB (1,048,576 bytes) of figures per run. KB and MB in this spec mean 1,024 and 1,048,576 bytes.

**PNG check** (in `--record` and the build): the file starts with the 8-byte PNG signature; it is a sequence of whole chunks, each with a length that fits in the file and a correct CRC; every chunk type is in the allow-list `IHDR`, `PLTE`, `IDAT`, `IEND`, `tRNS`, `gAMA`, `cHRM`, `sRGB`, `pHYs`, `bKGD`; there is exactly one `IHDR`, it is first, its length is 13, and its width and height are each between 1 and 4,096; its bit depth is valid for its colour type, and its compression and filter are 0 and its interlace 0 or 1; there is at least one `IDAT`; `PLTE`, if present, comes before the first `IDAT`; `IEND` is last, of length 0, and nothing follows it. As F-001e's "PNG chunk filter" also requires, these chunks have these lengths and appear at most once: `gAMA` 4, `cHRM` 32, `sRGB` 1, `pHYs` 9, `bKGD` 1, 2 or 6, `tRNS` 1 to 256, `PLTE` 3 to 768 and a multiple of 3; and the concatenated `IDAT` data is exactly one complete zlib stream with nothing after it, inflating to no more than the image's raw size (a filter byte per row, per Adam7 pass when interlaced) plus 1,024 bytes. Anything else is refused. Figures are not passed through the text scan: their bytes are binary, and the chunk allow-list is what keeps text out of them.

### Scorecard

`research publish --scorecard <eval_id>` (F-001e) writes a folder containing `scorecard.json` and `export.json` (`kind` `scorecard`, `id` the `eval_id`). `eval_id` matches `^eval-[0-9]{8}T[0-9]{6}Z$`.

**Types are normative in F-001e**, section "Scorecard types" (at `74d5d82`): every path, type and null rule there applies here, and `--record` and the build re-check all of them on the exported `scorecard.json`. Any path not in that table (including every field F-001e drops by default: `fingerprint.sha256`, `fingerprint.config.git.commit`, `fingerprint.config.git.dirty`, `fingerprint.config.prompts`, `fingerprint.config.questions_sha256`, `baseline.fingerprint`, `questions[].run_ids`) fails. F-001e's table refers to report-schema definitions that are private, so the ones the re-check needs are restated here:

- `utc_timestamp`: `^[0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{2}:[0-9]{2}:[0-9]{2}(\.[0-9]{1,6})?Z$`;
- `dataset_name` (`runs[].dataset.name`): `^[a-z0-9][a-z0-9-]{0,62}$`;
- `runs[].dataset.source` and `runs[].dataset.licence`: strings of 1 to 200 characters (the D6 gate then narrows them);
- `runs[].dataset.visibility`: `public` or `private` (the gate then requires `public`);
- `run_id`, the question `id` pattern, `status` and `checklist_tag`: as in F-001e's table and "Enumerations".

The site adds only these rules of its own:

- `eval_id` equals the export's `id`.
- At least one `runs[]` entry is non-null. A null repeat (`run_id: null`, `status: null`, no `dataset` or `models`) is skipped by the gate and by the harness count, as publish skips it.
- Enum values are as in "Enumerations".

**What the page shows** (one table, one row per question, plus a header):

| Shown | From | When null |
|---|---|---|
| Date | `created_at` as `YYYY-MM-DD` | — |
| Repeats per question | `k` | — |
| Harness | count of non-null `runs[].models.harness` per value, e.g. "LangGraph agent (50)"; one value per harness present, in the order `langgraph`, `claude-code` | — |
| Models | `fingerprint.config.models.analyst`, `fingerprint.config.models.critic` | — |
| Seed | `fingerprint.config.seed` | — |
| Per question: correct | `correct / n_repeats` | — |
| Per question: trap recall | `trap_recall.x / trap_recall.n` | "n/a" when n = 0 |
| Per question: critic precision | `critic_precision.x / critic_precision.n` | "n/a" when n = 0 |
| Aggregate | `aggregate.score ± aggregate.se` | "± n/a" when `se` is null |

Everything else (`caps`, `package_version`, `trap_handled`, `unreviewed_trap_passes`, `unscored_passes`, `statistic_mismatches`, `other_issues`, `baseline`, `dropped`) is type-checked but not shown.

**Number formatting** (fixed, so `--check` is deterministic): counts as integers, `x / n`; `aggregate.score` and `aggregate.se` with exactly two decimal places, rounded half away from zero **from the number's shortest round-trip decimal form** (JavaScript's `String(x)`), so 0.125 → "0.13" and 0.135 → "0.14"; no percentages.

### Where the synthetic data comes from

Checked in research-agent `main` (`src/research_agent/data/synth.py`, read only, 11 Nov 2026): the generator uses **no Databento-derived parameters**. It reads no files; it is a seeded random generator with hand-set planted effects and traps, and its calendar follows public exchange conventions. Publishing synthetic results is therefore not publishing derived data.

## Manifest

`projects/research-agent/published.json`, written by `--record` and `--record-scorecard`, edited by the owner only for `alt` and `role`. Dates are `YYYY-MM-DD` (UTC); timestamps UTC with `Z`. Runs are keyed by run id; `files` maps each run-relative path to its sha256; `alt` maps each figure path to its alt text.

```json
{
  "manifest_version": "1.0.0",
  "runs": {
    "20261111T143000Z-a1b2c3": {
      "checked": "2026-11-12",
      "export_digest": "9f2c…64 hex…",
      "tool_version": "0.1.0",
      "exported_at": "2026-11-11T15:04:05Z",
      "role": "trap_caught",
      "files": {
        "calls/3/out/vol_by_minute.png": "a1b2…64 hex…",
        "report.json": "c3d4…64 hex…",
        "report.md": "e5f6…64 hex…"
      },
      "alt": {
        "calls/3/out/vol_by_minute.png": "Bar chart of realised volatility by minute after the open; the first 30 minutes are higher."
      }
    }
  },
  "scorecard": {
    "eval_id": "eval-20261111T150000Z",
    "checked": "2026-11-12",
    "export_digest": "7b8a…64 hex…",
    "tool_version": "0.1.0",
    "exported_at": "2026-11-11T16:00:00Z",
    "files": { "scorecard.json": "0a1b…64 hex…" }
  }
}
```

`role` is optional; `scorecard` is absent until one is recorded. The build refuses unknown keys, a missing or empty `alt` entry for a listed figure, and an `alt` entry for a path that isn't a listed figure.

## The publish flow

1. In the private repository, `research publish <run_id>` writes the export to a folder outside this repository and prints the owner checklist and the export digest.
2. **The owner reads every file in the export**: the report text, every figure, and the JSON. This is the last check before the content is public (D2).
3. In this repository, on a new branch: `node build.mjs --record <export-dir> --expect <export digest>` (new). It first runs **every check the build would run** on the would-be result, without writing anything: the digest matches; the export contract (regular files only, `export.json` fields, exact file set, every `sha256` and `bytes`, patterns, sizes, the PNG check, enumerations); the `report.json` field checks; the D6 gate; the output scan and the employer denylist (and `.denylist.local`, below) over the exported text and over the pages the build would render from it. Only if all pass does it copy exactly the listed files, as the Buffers it read and at their run-relative paths, into `projects/research-agent/runs/<run_id>/`, and add the run to `published.json` with today's date, the digest, `export.json`'s `tool.version` and `exported_at`, each file's sha256 and an empty alt text per figure. The writes are staged with rollback. It refuses a run id already in the manifest.
4. The owner writes each figure's alt text and the optional role in `published.json`, then runs `npm run build` and `npm test`, and commits. The build refuses an empty alt text.
5. Push and open a PR to `main`. Pushing publishes the export in this public repository (D2); the PR is the record and runs CI.

**Scorecard:** `node build.mjs --record-scorecard <export-dir> --expect <export digest>`, the same checks for a scorecard, into `projects/research-agent/scorecard/`. It replaces the published scorecard (only the newest is shown, so only one is kept).

**Re-exporting a published run** (for example after F-001e changes its export format, same run id): read the new export, then `node build.mjs --record <export-dir> --expect <export digest> --replace`. It replaces the run's files, resets the checked date and digest, keeps alt text for figures whose hash is unchanged and empties it for changed or new ones (so they must be re-read). The earlier version stays in git history. A corrected analysis is a new run with a new run id, not a re-export.

**Unpublishing:** delete the run's directory and its manifest entry; the next build removes every output for it from the site (D4). Git history keeps it.

**Local denylist:** whenever `.denylist.local` exists (gitignored), `--record` and every local build check it. It is parsed and matched as F-001e's "Denylist format": UTF-8, one term per line, each line stripped of whitespace, blank lines and lines starting with `#` skipped; each term matched case-insensitively (Unicode case folding) as `(?<!\w)` + the regex-escaped term + `(?!\w)`. A file with no terms checks nothing (unlike F-001e, where the denylist is required, because here it is an optional extra). It is checked against the exported text, the rendered pages, and `published.json` (alt text and roles included). Terms the owner wants caught are thus never written into this public repository. CI can't see that file, so it is a local check only; the existing in-repository employer denylist (`employerMention`) still runs in every build.

**Curation (runbook note, not a build rule):** aim for three to five runs that show the whole loop: one where the critic catches a planted trap, one rejected plan, and one clean pass, using the manifest roles.

**`.gitattributes`:** exactly these two lines, so git never rewrites line endings in checked bytes:

```
projects/** -text
public/projects/** -text
```

## Edge cases

- **No runs yet.** Before launch the showcase builds with the `empty.runs` message and no scorecard section; after launch this can't happen (D9).
- **Only Claude Code harness runs.** Every run and the scorecard show their harness, so nothing implies a LangGraph run that wasn't one. Whether launch waits is open question 2.
- **Question text with Markdown or HTML.** Escaped plain text everywhere (body, titles, cards, JSON-LD, meta), never markup (D7b).
- **Very long reports.** No truncation; the 30 KB gzip cap fails the build (and `--record`), and the owner decides whether to publish.
- **An export pushed by mistake.** It is public from the push (D2). Unpublishing removes it from the site; removing it from git history would need a force-push and is out of scope; a leaked key is rotated, not scrubbed.
- **Clock and dates.** Displayed dates come from the files (`finished_at`, `created_at`, the manifest's checked date), never the build clock, so `--check` stays deterministic.
- **Schema minor versions.** A `report.json` with a newer 1.x minor version and extra optional fields is accepted; only the fields listed are read. A new enum value fails until "Enumerations" adds it.
