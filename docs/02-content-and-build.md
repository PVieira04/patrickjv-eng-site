# 02 — Content and build

## One source of truth

`content.json` holds every piece of approved copy: person (name, headline, tagline, location, links), about, stats, work, side projects, background, skills, the Quick answers (`faq`) and the footer privacy note (`privacy`). It was drafted from Patrick's LinkedIn source files, then reframed to be **employer-agnostic** at his request: the site describes what he is good at and has done, never who employs him.

The visible page body (`public/index.html`) is **hand-written** — it is the chosen design and its markup is specific to it. Everything else that carries the copy is **generated** from `content.json` by `build.mjs`, and the build parses the hand-written page to verify that it still shows every item.

## What the build generates

| Output | Contents |
|---|---|
| Head metadata inside `index.html` | `<title>`, meta description, canonical link, Open Graph (`og:title`, `og:description`, `og:url`, `og:site_name`, `og:image:alt`) and Twitter title/description — all from `content.json`, so they cannot drift from the copy |
| JSON-LD `@graph` inside `index.html` | `ProfilePage`, `WebSite`, `Person` (with `identifier: did:web:patrickjv.com`, `alternateName`, `disambiguatingDescription`, `hasOccupation`, `address` with `addressCountry: "GB"`, `email`, `sameAs`, `knowsAbout`), `FAQPage` |
| WebMCP data (`var d = …`) inside `index.html` | Profile, work, skills, FAQ (from `lib/agent-data.mjs`) and the tool list — names, titles, descriptions, input schemas and `readOnlyHint` annotations taken from the MCP server's own `tools()` in `mcp/handler.js` (the page adds one sentence to `request_intro`'s description about the in-browser confirmation). The build fails if the server gains a tool the page has no counterpart for, or if a data tool is not read-only. |
| `public/index.md` | The whole page as clean Markdown, ending with the privacy note |
| `public/llms.txt` | LLM briefing: summary, disambiguation line, work, side projects, background, Quick answers, links, privacy note, machine-readable endpoints (Markdown, sitemap, MCP) |
| `public/sitemap.xml` | One URL with `lastmod` |
| `public/robots.txt` | `Allow: /`, `Content-Signal: search=yes, ai-input=yes, ai-train=yes`, sitemap link |
| `public/_headers` | Security headers on `/*`; one CSP rule per exact path — the page policy (sha256 hashes of the page's one inline `<style>` and one inline `<script>`) on `/` and `/index.html`, a baseline policy on each known non-HTML path, including one rule per file in `public/fonts/` (no `/fonts/*` wildcard, so a missing font path gets only the 404 page's policy and no 30-day cache); explicit UTF-8 content types; `Vary: Accept`; cache lifetimes for fonts and images (see [05](05-quality-and-audits.md#security-headers)) |
| CSP `<meta>` in `public/404.html` | The 404 page's own policy (hash of its inline `<style>`), kept in sync by the build — the 404 page is served at arbitrary paths, which no per-path `_headers` rule can name |
| `build-state.json` | `{ hash, date }`: the sha256 of the content-bearing outputs (rendered with a placeholder date) together with the sha256 of each image the page references, and the date that combination was first built |

**`dateModified` / `lastmod` are content-addressed, over content only** (review C3-F10). The build renders everything with a placeholder date and hashes the content-bearing outputs — `index.html`, `index.md`, `llms.txt`, `sitemap.xml` and `robots.txt` — together with the sha256 of every image the page references (portrait variants, share card, favicons and icons; found in the rendered page's `src`, `srcset`, `href` and `og:`/`twitter:image` values). Not content, so excluded: `_headers`, the 404 page, the fonts, `security.txt`, `mcp-registry-auth` and `did.json` (frozen, with its own hash check). If the hash matches `build-state.json`, the recorded date is kept; otherwise today's date is used and recorded. The date therefore moves when the page, its machine-readable copies or a referenced image change (e.g. a new portrait under the same file name) — not for a header, font, 404-page or `security.txt` change — a rebuild converges in one run, and `--check` depends on neither git nor the clock.

JSON spliced into a `<script>` is escaped (`<` as `\u003c`, plus U+2028/U+2029), so copy containing `</script>` can never close the element.

## Safety checks (the build fails if any is violated)

All checks run **before anything is written**: a validation failure writes nothing (`BUILD FAILED (validation failed — nothing written)`). If every check passes, the changed files are written to temporary names and then renamed into place. That is **not transactional**: if an I/O error interrupts the renames, the build removes its temporary files and restores the files it had already replaced, then reports the failure; if that rollback itself fails it says the outputs may be partially written — rerun the build.

1. **Section-aware copy check.** A small HTML parser walks the page. Each `content.json` item must be the **whole visible text of its own element in its own section** — masthead name/headline/tagline, contact strip, About, In figures (value and label separately), Work (title, summary, tags), Side projects, Background, Skills, Quick answers and the footer privacy note — in order and with the right count. Hidden content (`hidden`, `aria-hidden="true"`, comments) does not count, and a value cannot match as a substring of another (e.g. `40` inside `1,400+`). Any `content.json` string that no check covers is itself an error, so a new field cannot go unchecked. Coverage is tracked by **field path** (e.g. `work.2.tags.1`), not by value, so a new field is reported even if its value duplicates one that is already checked.
2. **Link targets.** The hero buttons, contact strip and footer must link to exactly the approved LinkedIn, GitHub and `mailto:` targets, and *any* `mailto:`, LinkedIn or GitHub link anywhere on the page must use the approved target — a changed address fails even if the visible text is unchanged.
3. The page, `404.html`, `index.md` or `llms.txt` contains a term from a short employer **denylist**. This catches the known names only — it is a tripwire, not a general detector; employer-agnostic copy still depends on review.
4. The page does not have exactly one `<h1>`.
5. `public/.well-known/did.json` no longer matches its frozen sha256.
6. **Inline-code guards** (attributes parsed in any case or quoting): the page must have exactly one inline `<style>` and one executable inline `<script>` (JSON-LD is a data block); the 404 page exactly one `<style>` and no script. Any `style="…"` attribute, `on…` handler attribute, external stylesheet, external script or non-JavaScript script type fails — the CSP would block it.
7. **`_headers` guards:** no `! Header` detach lines (production ignores them — see [06](06-operations.md#incidents)), no `Content-Security-Policy` on `/*`, no CSP on any wildcard or placeholder rule (every CSP rule is an exact path), and no path pattern given a CSP by two rules.
8. **404 page:** exactly one `<h1>`, `<meta name="robots" content="noindex">`, and a link to `/`.
9. **`security.txt` `Expires`** must exist, parse as a real date, and be more than 30 days and at most 366 days ahead (RFC 9116 recommends less than a year).
10. `--check` mode: any generated file (including `build-state.json`) is out of date.

`npm test` runs `node build.mjs --check` first; `npm run deploy` (manual) runs `npm test` first, and every Workers Builds build runs `npm ci && npm test` before its deploy command — stale or broken copy cannot be deployed. `test/build.test.mjs` (26 tests) covers the checks above: a hidden or `aria-hidden` section, a changed `mailto:`/LinkedIn target, a removed, commented-out or moved skill, the `40` vs `1,400+` substring case, a removed privacy note, an unchecked `content.json` string and a new field whose value duplicates a checked one, the `_headers` guard (fixtures with a CSP on `/*`, a detach line, a wildcard CSP rule and a duplicate CSP path) and the per-font rules, the page's WebMCP request headers, inline-code bypasses, JSON escaping, `security.txt` bounds, one-run convergence, referenced-image bytes moving the date and non-content changes (404 page, font, `security.txt`, `mcp-registry-auth`, an unreferenced image) leaving it alone, nothing written on validation failure, rollback after an injected rename failure, and generated head metadata. Guards were proven by deliberately breaking them and watching a test fail ("revert-and-fail"). `test/webmcp.test.mjs` (5 tests) runs the page's WebMCP script in a VM with a stubbed `document.modelContext`.

## Shared data module

`lib/agent-data.mjs` maps `content.json` to the public data offered to agents. Both the page's WebMCP tools (via the build) and the MCP server import it, so the two surfaces always expose identical facts.

**The CV** (`/cv`, and `/cv.pdf` from the homepage's CV button) has its own source, **`cv.json`**: headline, profile, roles, projects, skills, education and spoken languages; name, location and contact links come from `content.json`. `npm run build` renders `public/cv.html` (A4 print stylesheet, own CSP rule in `_headers`, linked from `llms.txt`, `index.md` and the sitemap, and as `links.cv` in the MCP/WebMCP profile). **The CV names employers; nothing else does** — the `BANNED` employer guard still covers the page, 404, `index.md` and `llms.txt`, and `cv.json` is never read by the agent surfaces. After changing `cv.json`, run `npm run build`, then **`npm run cv`**: it serves `public/` on localhost, prints `/cv` with headless Chromium (pinned `playwright-core`; install its browser once with `npx playwright-core install chromium-headless-shell`; on WSL without system libraries set `LD_LIBRARY_PATH=$HOME/.local/opt/pw-libs/root/usr/lib/x86_64-linux-gnu`), **refuses to write a PDF of more than two pages**, and records the hashes in `designs/images.json`. `test/images.test.mjs` fails if `cv.html` changed without regenerating the PDF, and counts the committed PDF's pages from its bytes (1–2). The PDF is not byte-reproducible (Chromium stamps a creation date), so it is pinned by its inputs.

**Regenerate with `npm run images`** (`designs/make-images.mjs`): icons first, then the card (which embeds `icon-192.png`), then it records the sha256 of every input and output in `designs/images.json`. Reproducible since 7 Oct (review R53): `sharp` is a pinned devDependency (`0.35.4`, the same version wrangler already installs), and the card's fonts come only from `designs/og/fonts/` (IBM Plex Sans Regular/SemiBold, Mono Regular/Medium TTF, OFL) — the script points fontconfig at a config listing that folder alone, so installed system fonts cannot change the result (checked by removing a font: the card changed although the same font is installed system-wide). `test/images.test.mjs` fails if an input changed without regenerating (the icon SVG, a generator, a font, the sharp version, `photo.webp`, `icon-192.png`, or the card's `content.json` fields `person.name`/`headline`/`tagline` — other copy edits do not count) or if an image was edited by hand; it compares hashes only, so CI never runs sharp. The six candidate designs in `designs/` are an archive only — not built or deployed, and they still contain obsolete copy and Google Fonts requests (see `designs/PROVENANCE.md`).
